# Implementation Notes — NZA-ADMIN-v1.1

Per the Deviation Protocol (NZA-ADMIN-v1.1-COWORK-IMPL SS0.3): every deviation from the spec gets a dated entry here — what the spec said, what was built, why. Ej reviews this at each phase gate.

---

## Phase 0 — Discovery (July 2026)

- **Role model.** Spec assumed Cognito Groups (`super_admin`, `support`, `read_only`). Reality: `Backend/shared/auth.js` uses a single JWT custom claim (`custom:role`), checked via `hasRole(actor, allowedRoles)`. No `AWS::Cognito::UserPoolGroup` resources exist anywhere in `infra/template.yaml`. **Decision (Ej, confirmed):** extend the claim-based model rather than migrate to Cognito Groups — add `support`/`read_only` as additional values of `custom:role`, not as a new auth mechanism. Phase 2 (task #119) will build against this.
- **Account deletion.** Spec assumed `nianza-account-deletion-lambda` exists and Phase 4 extends it. Reality: no such Lambda existed — `Backend/admin/users/handler.js`'s `handleDeleteInitiate` only wrote an audit-log intent row and admitted in its own comment that the data sweep wasn't built. **Built July 2026:** a real cross-table + Cognito deletion sweep directly inside `admin/users/handler.js` (`sweepUserData`), not a separate Lambda — per-user data volume (a handful of children, a few hundred rows) is well within one Lambda invocation, so a dedicated sweep/reconciler Lambda was judged to be more infra than the problem warrants. Known gap: does not yet touch RevenueCat (no billing integration existed at the time) — flagged in the handler's own return payload.
- **User lookup.** Spec assumed `/admin/v1/users` was a stub. Reality: `admin/users/handler.js` already had real search/detail/list functionality built (Phase 0 backend work, pre-dating this spec review).

## Phase 1 — Billing Pipeline (July 2026)

Built: `Backend/shared/billing-metrics.js` (MRR/ARR/at-risk-MRR per spec SS3.3), `Backend/billing/webhook/handler.js` (`nianza-billing-lambda`), `Backend/billing/reconcile/handler.js` (`nianza-billing-reconcile`), `Backend/admin/billing/handler.js` (admin summary/events/failed-payments endpoints), plus the corresponding `infra/template.yaml` resources (Secrets Manager, S3, DynamoDB, 3 Lambdas). Dashboard's Revenue section now reads real data (`AdminPortal/src/pages/dashboard.tsx`), replacing the old projected-from-status-counts estimate.

Deviations from the spec's literal text:

- **Resource naming.** Spec names: `nianza-billing-lambda`, `nianza-billing-reconcile`, S3 bucket `nianza-billing-raw`, secrets `nianza/revenuecat/webhook-secret` and `nianza/revenuecat/api-key`. Built names: `nianza-billing-webhook-${Environment}`, `nianza-billing-reconcile-${Environment}` (Lambda `FunctionName`, matching every other Lambda's `nianza-<area>-<subarea>-${Environment}` convention in this codebase), bucket `nianza-billing-raw-${Environment}-${AWS::AccountId}` (S3 bucket names are globally unique across all AWS accounts — every other bucket in this template already suffixes with account id for exactly this reason; the spec's literal name would likely fail to create), secrets `nianza/revenuecat/webhook-secret-${Environment}` and `nianza/revenuecat/api-key-${Environment}` (env-suffixed so dev and prod don't share a secret).
- **Admin billing route path.** Spec notation: `GET /v1/admin/billing/summary`. Built: `GET /admin/v1/billing/summary`, matching the path prefix every other admin endpoint in this API actually uses (`/admin/v1/users`, `/admin/v1/subscriptions`, etc.) — the spec's own path ordering doesn't match its own baseline description elsewhere.
- **Webhook secret provisioning.** The webhook shared secret is auto-generated by CloudFormation (`GenerateSecretString`) rather than manually created, since we control both sides (we mint it, then paste it into RevenueCat's webhook config UI) — no manual creation step needed for that one. The RevenueCat *API key* secret (needed for reconciliation + Phase 3 actions) genuinely can't be generated by us — it's created as a placeholder (`REPLACE_ME_MANUALLY_IN_CONSOLE`) that Ej must overwrite in the Secrets Manager console once a live RevenueCat project exists.
- **Reconciliation job scope.** `nianza-billing-reconcile` is fully built and wired to run nightly, but detects the placeholder API-key secret and no-ops (writing a `RECONCILIATION_NOT_CONFIGURED` marker row instead of failing loudly) until Ej connects a real RevenueCat project and replaces the placeholder. This is a genuine gap, not a deferred build — the code path for real reconciliation is written and will activate the moment the secret is real.
- **Product ID mapping — confirmed live, July 28 2026.** Checked the actual NIanza RevenueCat project (`app.revenuecat.com/projects/86547d89`) via browser: real product identifiers are `monthly` and `yearly` (not `nianza_monthly`/`nianza_annual`, and notably `yearly` not `annual`), created July 28 2026 under a **Test Store** app — no real App Store/Play Store app is connected yet, just RevenueCat's built-in sandbox store. `REVENUECAT_MONTHLY_PRODUCT_ID`/`REVENUECAT_ANNUAL_PRODUCT_ID` in `infra/template.yaml` are set to `monthly`/`yearly` to match. **No webhook integration exists in the RevenueCat project yet** (Integrations → Webhooks shows only "Add new configuration") — see the setup checklist below.
- **Event feed without a type filter.** Spec's GSI1 design (eventType PK + eventTimestamp SK) makes "newest-first across all event types" not a single clean query. `GET /admin/v1/billing/events` without `?eventType=` falls back to a bounded Scan + in-memory sort — the same small-scale tradeoff `admin/metrics` and `admin/subscriptions` already make elsewhere in this codebase. Revisit if event volume ever makes this slow.
- **admin/metrics/handler.js left untouched.** The old `revenue.projectedMrr`/`projectedArr` block still exists server-side and is still served by `GET /admin/v1/metrics` — it's superseded by `GET /admin/v1/billing/summary`, not deleted, in case the projection-vs-real comparison is useful during RevenueCat rollout. The Dashboard no longer renders it.
